1. Вас пригласили настроить мониторинг на проект. На онбординге вам рассказали, что проект представляет из себя 
платформу для вычислений с выдачей текстовых отчетов, которые сохраняются на диск. Взаимодействие с платформой 
осуществляется по протоколу http. Также вам отметили, что вычисления загружают ЦПУ. Какой минимальный набор метрик вы
выведите в мониторинг и почему?

### Ответ 1.
Мнинмальный набор метрик для отслеживания работоспособности сервиса:
- http_requests_total по кодам (2хх/4хх/5хх)  – чтобы понимать, доступен ли сервис и нет ли ошибок;
- http_request_duration_seconds – для оценки времени ответа;
- cpu_utilization_percent – так как вычисления нагружают CPU нужно отслеживать утилизацию;
- memory_usage_bytes – чтобы понять, не упирается ли система в память;
- disk_free_bytes и disk_usage_bytes - чтобы не допустить заполнения диска;
- IOPS - количество операций ввода/вывода, метрика позволяет отслеживать работоспособность оборудования\4
- disk_inodes_free – особенно важно для Linux, если создаётся много мелких файлов отчётов.

2. Менеджер продукта посмотрев на ваши метрики сказал, что ему непонятно что такое RAM/inodes/CPUla. Также он сказал, 
что хочет понимать, насколько мы выполняем свои обязанности перед клиентами и какое качество обслуживания. Что вы 
можете ему предложить?

### Ответ 2.
Для менеджера можно сделать отдельный дашборд с нужными ему метриками (SLI/SLO):

- SLI (service level indicator) – доля успешных HTTP-запросов (2xx/все), время ответа.
- SLO (service level objectives) – например, 99% запросов должны завершаться за < 200 мс.

А технические метрики переименовать в более понятные:

- RAM - «Использование оперативной памяти, %»;
- inodes - «Свободное место под файлы (иноды)»;
- CPUla (load average) - «Средняя загрузка процессора».

4. Вы, как опытный SRE, сделали мониторинг, куда вывели отображения выполнения SLA=99% по http кодам ответов. 
Вычисляете этот параметр по следующей формуле: summ_2xx_requests/summ_all_requests. Данный параметр не поднимается выше 
70%, но при этом в вашей системе нет кодов ответа 5xx и 4xx. Где у вас ошибка?

### Ответ 4.
Если в системе нет кодов 4xx и 5xx, но метрика показывает всего 70%, это означает, что остальные 30% запросов приходятся на другие классы кодов - редиректы 3хх и информационные ответы 1хх.
Необходимо исправить формулу, например так:

SLA = (summ_all_requests-summ_5xx_4хх_requests)/summ_all_requests
  
P.S. Наличие 4xx ошибок не всегда говорит о недоступности сервиса

5. Опишите основные плюсы и минусы pull и push систем мониторинга.

### Ответ 5.
Push

Плюсы:
- Простая репликация данных в разные системы мониторинга.
- UDP — это менее затратный способ передачи данных, из-за чего может возрасти
производительность сбора метрик.
- Более гибкая настройка отправки пакетов данных с метриками.

Минусы
- Трудно обнаружить недоступность агента (нет данных – не значит, что всё плохо).
- Сложнее управлять потоком данных (перегрузка сервера).
- Меньше контроля над частотой и временем сбора.
- 
Pull

Плюсы:
- Легче контролировать подлинность данных.
- Легче обнаружить недоступность агента.
- Возможность настройки единого proxy server до всех агентов с TLS.
- Упрощённая отладка получения данных с агентов.

Минусы:
- Сложнее масштабировать горизонтально.
- Не подходит для кратковременных задач.
- При сетевых проблемах теряются все показатели за время простоя системы.

9. Изучите список [telegraf inputs](https://github.com/influxdata/telegraf/tree/master/plugins/inputs). 
Добавьте в конфигурацию telegraf следующий плагин - [docker](https://github.com/influxdata/telegraf/tree/master/plugins/inputs/docker):
```
[[inputs.docker]]
  endpoint = "unix:///var/run/docker.sock"
```

Дополнительно вам может потребоваться донастройка контейнера telegraf в `docker-compose.yml` дополнительного volume и 
режима privileged:
```
  telegraf:
    image: telegraf:1.4.0
    privileged: true
    volumes:
      - ./etc/telegraf.conf:/etc/telegraf/telegraf.conf:Z
      - /var/run/docker.sock:/var/run/docker.sock:Z
    links:
      - influxdb
    ports:
      - "8092:8092/udp"
      - "8094:8094"
      - "8125:8125/udp"
```

После настройке перезапустите telegraf, обновите веб интерфейс и приведите скриншотом список `measurments` в 
веб-интерфейсе базы telegraf.autogen . Там должны появиться метрики, связанные с docker.

Факультативно можете изучить какие метрики собирает telegraf после выполнения данного задания.
